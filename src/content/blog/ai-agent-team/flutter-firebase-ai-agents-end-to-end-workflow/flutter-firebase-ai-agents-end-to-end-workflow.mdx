About fourteen of the thirty agents touch one small feature, and the handoffs are the point. The business analyst's open question becomes the architect's rule. The rule becomes a test, the test becomes a security check, and the check becomes an attack that runs on every push. On MSDevBuild Eats, that chain finds a cancel rule enforced in the screen but bypassable in both the domain and the Firestore rules.

Back to the six words that started this series: "users can cancel an order."

[The planning and analyst agents](/blog/ai-agents-project-planning-business-analyst-architect) found that the rule they imply lives in one screen. This part walks the same feature through every agent that touches it, start to finish, with what each one reads, what it hands to the next, and what it finds in the real code.

A small feature on purpose. Grand examples hide the seams, and the seams are where a workflow differs from thirty separate tools.

## Day one: the question, and the rule

The business analyst agent got the six words and `OrderStatus`. It listed all seven states and refused to guess the hard part:

> *Can a customer cancel after the restaurant starts preparing? If yes, who absorbs the cost?*

A person answered it in the same meeting: cancellation is allowed only while the order is `placed` or `confirmed`. That answer is the business rule, and it is the input to everything downstream.

The solution architect agent put it where every caller would meet it:

```dart
// lib/domain/entities/order.dart
bool get canBeCancelled =>
    status == OrderStatus.placed || status == OrderStatus.confirmed;
```

`cancelOrder` returns a failure when `canBeCancelled` is false, and `AGENTS.md` gains a line: *business rules live on entities or use cases, never in a screen's state.* The database agent confirmed no schema change was needed. That is also a useful output, because the absence of a migration is information.

## Day two: the code, the tests, and the hole underneath

The Flutter agent's change was small: the screen's `canCancel` now reads `order.canBeCancelled` instead of repeating the condition. One rule, one place.

The testing agent read the requirements before the code and wrote five tests named after the criteria. AC-3, "cancelling a preparing order is refused", failed against the existing `cancelOrder`, which accepted any status. That failure is what [testing from requirements](/blog/ai-agents-testing-code-review-performance-ui) is for, and it went green once the architect's rule landed.

Then the security agent read the deployed rules, and found the same rule missing one layer further down.

## The command that finds the third layer

```bash
sed -n 82,88p firebase/firestore.rules
```

```text
      allow update: if signedIn() && (
        ownsRestaurant(resource.data.restaurantId) ||
        isRider() ||
        // A customer may only cancel their own order or mark it rated.
        (resource.data.userId == request.auth.uid &&
         request.resource.data.diff(resource.data).affectedKeys()
           .hasOnly(['status', 'timeline', 'isRated']))
      );
```

The comment says a customer may only cancel or rate. The rule says something wider: a customer may change `status`, `timeline` and `isRated` on their own order to **any value, from any current state.** It limits which fields change, never what they change to. A customer who writes to Firestore directly, skipping the app, can set a `preparing` order to `cancelled`, or to `delivered`.

So after day two, the cancel rule held in the screen and in the domain, and not in the database. The exploit path is concrete: sign in as the order's customer, write `{status: 'cancelled'}` to an order that is `preparing`, and the write succeeds.

The fix states the transition, not just the fields:

```javascript
// A customer may cancel an order that has not started cooking, or rate one.
(resource.data.userId == request.auth.uid && (
  (request.resource.data.status == 'cancelled' &&
   resource.data.status in ['placed', 'confirmed'] &&
   request.resource.data.diff(resource.data).affectedKeys().hasOnly(['status', 'timeline'])) ||
  request.resource.data.diff(resource.data).affectedKeys().hasOnly(['isRated'])
))
```

The penetration testing agent turned the finding into two permanent tests against the emulator: a customer cancelling their own `preparing` order (denied), and a customer setting their own order to `delivered` (denied). Both fail against today's rules and pass against the fix, and both run on every push from then on. That is the difference between a finding and a guarantee.

The privacy agent looked at the optional cancellation reason the product team wanted. Free text from a customer is unpredictable personal data, because people type anything. It went into `privacy/data-inventory.md` with a purpose and a retention period before it shipped.

## Day three: shipping

The localization agent caught a new string built the old way, `'Cancel order ' + order.id + '?'`, and turned it into one ICU message with a description for the translator, the same pattern [the reach agents](/blog/ai-agents-accessibility-localization-documentation-seo) found in `partner_bloc.dart`. The accessibility agent found the confirmation dialog's close control had no name, and wrote the four-step TalkBack script; it took ten minutes to run.

The release agent wrote the notes from the merged pull requests and the requirements file, so they said "you can now cancel an order before the restaurant starts preparing it" rather than naming a file. The analytics agent added `order_cancelled` to `analytics/events.yaml` with its place in the order funnel, before any code logged it.

## What did the whole thing actually cost?

Here is the honest accounting.

**This feature** took about a day longer at the front than writing the screen straight away. That day bought:

- a business rule nobody had actually decided;
- the rule moved from one screen into the domain;
- a hole in the Firestore rules that the domain fix alone would have left open;
- two attack tests that keep it closed;
- an untranslatable string and an unnamed button caught before release.

**Setting up the agents** is the larger cost, and it is front-loaded. The first four agents (architect, review, testing, security) do most of the work; the rest are added when a real failure justifies them. No clean multiple comes out of one feature, and none is claimed here.

What the series does show is a pattern. Every failure in it was cheap on the day it was created and expensive by the time it was found. Across ten parts, the agents found these in one real app:

| Found by | File | Finding |
| --- | --- | --- |
| Analyst, architect | `order_tracking_state.dart` | Cancel rule only in a screen's state |
| Database | `partner_state.dart` | Today's count streams every order ever placed |
| Firebase, security | `firestore.rules:76, 84` | Any rider reads and updates any order |
| Testing | `test/` | 93 tests; none cancels a `preparing` order |
| UI review | `rider_dashboard_screen.dart` | A failed load reads "No jobs right now" |
| DevOps | `app_config.dart` | Backend chosen by a code default |
| Release | `android-distribute.yml` | Tester notes are the last commit subject |
| Monitoring | `pubspec.yaml` | No crash reporting |
| Dependencies | `pubspec.yaml` | `uuid` imported by no file |
| Privacy | `data-inventory.md` | Promise narrower than the rules |
| Accessibility | `restaurant_card.dart` | Favourite button announces only "button" |
| Localization | `partner_bloc.dart` | A sentence built from English fragments |
| Prompt engineering | `monitoring.md` | Refusal condition buried mid-sentence |
| Security, pen test | `firestore.rules:82-88` | Customer can write any status on their own order |

None of these is exotic. All of them sat in a well-structured, tested, public codebase, because each belonged to a job nobody had been given.

## The mistakes worth skipping

Across ten parts, the same errors reappear in different costumes.

- **One giant agent.** Thirty responsibilities means no definition of done and a diff so wide the reviewer checks only the part they know.
- **Trusting a clean report without checking the input.** The repository's rules instead of the deployed ones; one identity instead of two.
- **An agent where a script belongs.** Licence scanning, secret detection, index checks. Deterministic work is faster, cheaper and unarguable as a hook.
- **A rule enforced in one layer.** The screen, or the domain, or the database. A cancel can arrive through any of them.
- **Doing the thinking after the shipping.** Rules written after the code, declarations before the analytics, crash reporting after launch.

## Which AI agents should you build first?

Not thirty. Build four, in this order, and use them for a month before adding a fifth.

1. **Solution architect.** Everything downstream inherits its decisions.
2. **Code review.** Fastest to show value; turns comments you type every week into a file.
3. **Testing.** Pointed at requirements, never at the implementation.
4. **Security.** By now it has real structure to reason about, so its findings are specific.

Then add whichever agent maps to the thing that hurt most last month. If you have never been bitten by a licence, do not start there; if a dependency once cost you four days, you know where to begin.

## Questions a tech lead will ask about this

1. **"Fourteen agents for one feature sounds heavy."** Most ran for minutes. The expensive ones were the analyst's question and the security review, and both found something.
2. **"Why did the domain fix not close the hole?"** Because Firestore rules are a separate entry point. A client can write to Firestore without going through your use cases.
3. **"Who answered the BLOCKING question?"** A person who owns the business rule. The agent's job is to ask.
4. **"Do the attack tests slow CI down?"** Seconds, against the emulator. They are the cheapest insurance in the pipeline.
5. **"Where do we start on Monday?"** The architect agent, and the test for your most important business rule at every layer it can be reached.

## What to do on day one

- Pick one business rule and list every layer a request can reach it through.
- Check that each layer enforces it: screen, domain, database rules.
- Write the attack test that fails if the database layer does not.
- Read your rules' comments next to their conditions; look for a comment wider than the code.
- Build the four agents before the fifth.

## Key takeaways

- The handoffs are the workflow. One agent's open question becomes the next agent's input.
- About fourteen agents touch one feature, not thirty. The rest have their own triggers.
- A business rule must hold in every layer a request can arrive through. The screen, the domain and the database rules are three different entry points.
- Every failure in this series was cheap on the day it was created. Put the check at the moment of creation.
- Start with four agents and let real pain pick the fifth.

## The next feature

A month later the restaurant pause feature arrives as one sentence. The analyst agent asks what happens to orders already placed. The architect puts `Restaurant.isAcceptingOrders` on the entity. The testing agent names its criteria first. The security agent checks the rules before the screen exists, and the pen test agent writes the attack test for a customer placing an order at a paused restaurant through Firestore directly.

It fails. It is fixed before release.

None of this is Flutter-specific. Swap Firestore rules for row-level security and `pubspec.yaml` for a `.csproj`, and the roles, handoffs and triggers stay where they are. The stack decides what the hooks look for. It does not change who is on the team.
