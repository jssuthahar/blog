One attacker. One food delivery backend on Azure. Five different ways in.

For each one, there's a specific, named Azure control that shuts it. Miss one, and the other four don't cover for it — each door guards a different thing.

## Attack 1: How do you stop a flood of junk and injection strings?

**Stopped by:** Azure Front Door WAF, running the OWASP managed ruleset at the edge. Traffic dropped here costs you nothing — no container spins up, no database connection opens.

**The catch:** WAF ships in **Detection** mode, which only logs. Switch it to **Prevention**, or it's a very expensive diary.

## Attack 2: What stops calls with no token?

**Stopped by:** Microsoft Entra ID. Your API validates the token's signature, issuer and audience against Microsoft's published keys — locally, in microseconds.

**The catch:** validate the `aud` claim, not just the signature. A valid token issued for a different app is still a valid token.

## Attack 3: What stops a real token asking for someone else's data?

This is the one people miss. The attacker signs in, legitimately, as themselves. Then they call `GET /orders/1043` — which belongs to someone else. Authentication passed. There's nothing wrong with their token.

**Stopped by:** an owner check in your own API. This bug is called **broken object level authorization**, and it's number one on the OWASP API Security Top 10.

```csharp
db.Orders.Where(o => o.UserId == me.GetObjectId())
```

Take the user id from the validated token — never from the body, the query string or a header. The moment the client can tell you who it is, the check is decoration.

## Attack 4: What stops someone searching your repo for keys?

**Stopped by:** Azure Key Vault plus a managed identity, so the repo holds a vault URI and nothing else. Turn on GitHub secret scanning too, and scan history, not just the latest commit — a key deleted in a later commit is still sitting in the repo.

## Attack 5: What stops someone dialling the database directly?

**Stopped by:** a private endpoint, with public network access set to `Disabled`. The server gets a private IP inside your VNet and no internet-facing address at all.

## Which default setting undoes door 5?

<Callout type="warning" title="“Allow Azure services and resources to access this server”">
  It sounds like it means *your* Azure resources. It doesn't. It means **any resource in any Azure subscription in the world** — including one an attacker creates in five minutes with a free trial. Leave it off, and use a private endpoint or explicit firewall rules.
</Callout>

## What should you check this week?

1. Is WAF in Prevention or Detection?
2. Can you fetch another user's record with your own valid token?
3. Is public network access `Disabled` on SQL, Storage and Key Vault?
4. Is "allow Azure services" off?
5. Is Microsoft Defender for Cloud on, so you hear about trouble before the invoice does?

## Key takeaways

- Five common attacks map onto five named controls: WAF, Entra ID, an owner check in your code, Key Vault, and a private endpoint.
- Owner checks are the one control authentication can't provide — a real, valid token is exactly what BOLA uses.
- WAF's default Detection mode only logs; switch it to Prevention.
- "Allow Azure services and resources" means every Azure tenant, not yours — keep it off.
- Run the five-question audit regularly, not once.
