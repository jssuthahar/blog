AI coding agents write a genuinely large share of the code shipped this year — GitHub, Anthropic, and OpenAI have all published numbers pointing the same direction. What gets talked about far less is what happens once more than one person, or even one person across more than one session, is generating code without anything tying those sessions together.

The short version: the agent doesn't stay consistent with itself unless you tell it how. That's true whether it's ten developers on an enterprise team or one person working solo across a few weekends. AGENTS.md is the fix, and it scales down to a hobby project just as well as it scales up to a codebase with hundreds of contributors.

## The same problem, at every scale

**Solo developer.** You ask your agent to build a login screen in January. It picks one state-management approach, one folder structure, one error-handling style. In April, working on a different feature in the same project, you ask again — and get a different answer. Not because the agent got worse, but because nothing carried the January decision forward. You're now doing code archaeology on your own project to figure out which pattern is "the real one."

**Small team, three to ten developers.** This is where it gets visible fast. One developer's agent reaches for Redux, another's reaches for Context, a third pulls in a state library nobody else on the team has used before — three individually reasonable choices for the same underlying problem. Duplicate API clients start appearing because nobody's agent can see what already exists two folders over. None of it looks like a bug in review; it looks like three people who never talked to each other, because in a sense, that's exactly what happened.

**Enterprise, dozens to hundreds of developers, possibly multiple squads.** Everything from the small-team case, except it compounds instead of staying contained. Different squads may not even know they've landed on different conventions until a cross-team feature forces two patterns to meet. Onboarding gets harder instead of easier, because a new hire isn't learning one set of conventions — they're reverse-engineering which of several competing ones is actually current.

Same root cause at every size: an AI agent making a locally reasonable decision with zero visibility into what already happened elsewhere — whether "elsewhere" is another developer's session or your own, three months ago.

## What AGENTS.md actually fixes

One file, read automatically before the agent generates anything, telling it the architecture, the one approved pattern for state and data, where things belong, and what already exists so it doesn't get rebuilt. Doesn't matter if you're writing Dart, TypeScript, C#, or Python, and it doesn't matter if you're a team of one or a team of two hundred — the mechanism is identical because the failure mode is identical.

The clearest comparison: it's the difference between handing someone repo access and saying "go," versus actually walking them through how the project is built. An AI agent needs the same walkthrough every session, because it doesn't carry yesterday's conversation forward on its own. AGENTS.md is that walkthrough, written once, read automatically forever after.

## How is this different from copilot-instructions.md?

If you've read the earlier post on custom instructions, you already know `.github/copilot-instructions.md` — and it's fair to ask why there's a second file that seems to do the same job. Short version: they overlap in purpose but differ in scope and who reads them.

| | `.github/copilot-instructions.md` | `AGENTS.md` |
| --- | --- | --- |
| Who reads it | GitHub Copilot only | Codex, Cursor, Copilot, Windsurf, Aider, and others — natively |
| Where it lives | Fixed path, repo root only | Root, plus optional nested files per subfolder/monorepo package |
| Origin | GitHub/Copilot-specific convention | Open, vendor-neutral standard |
| Claude Code | Not applicable — Copilot-only anyway | Needs a symlink or `@AGENTS.md` import; doesn't read it natively either |
| Best fit | Copilot-only, no plans to mix tools | Using, or might use, more than one AI coding tool |

If every developer is on Copilot and staying there, `copilot-instructions.md` is simpler and does the job. The moment a second tool enters the picture — someone trying Cursor, someone evaluating Claude Code — AGENTS.md stops being the "extra" file and becomes the one that saves you from maintaining two or three near-duplicate instruction files that quietly drift apart.

You can run both at once without conflict — Copilot reads its own file, other tools read the standard one. The only real cost is remembering to update both when a shared rule changes.

## A generic example, not tied to any framework

Here's roughly what a minimal one looks like, stripped down to the shape that applies regardless of stack or team size:

```markdown
# AGENTS.md

## Project
Web app, React frontend, Node/Express backend, PostgreSQL. Monorepo.

## Architecture
Feature-based folders, not type-based. Each feature owns its components,
hooks, and API calls — don't split a feature across /components and /hooks
at the top level.

## State management
Use the existing Zustand store in /src/store. Don't introduce Redux,
Context-based state, or a second store.

## API layer
All requests go through /src/api/client.ts. Don't call fetch() directly
in components, and don't create a second HTTP client.

## Error handling
API errors return a Result<T, Error> type, never throw across the
API boundary. Log unexpected errors through /src/lib/logger.ts.

## Testing
Vitest for units, Playwright for e2e. New features need at least one
unit test per new function in /src/api or /src/store.

## Off-limits
- Don't modify /prisma/migrations
- Don't add new npm dependencies without flagging it in the PR description
```

Swap the specifics and the same shape works for a Django backend, a Spring Boot service, a Flutter app, an Angular frontend, anything — solo project or shared repo. The categories don't change: stack, architecture, the one approved pattern for state/data, error handling, testing, and what's off-limits.

## How do you actually create the file?

The simplest version costs nothing: create `AGENTS.md` at the root of your repo, plain text, no special tooling required. That's the whole setup — any editor, any tool that reads it will pick it up automatically from that location.

If you're in VS Code with Copilot, there's a faster path: open Copilot Chat and type `/init`. It scans the repo and drafts a first version based on what it finds — dependencies, folder structure, whatever config exists already. Treat the output as a draft, not a finished file. It's genuinely good at picking up patterns that are already consistent in your code; it can't tell you which pattern to standardize on if your codebase already has two or three competing ones. That decision is still yours, on a solo project as much as a team one.

For a monorepo or a project with genuinely different sub-projects, nest additional `AGENTS.md` files in subfolders — the file closest to the code being edited takes priority over the root one. Shared rules stay in the root file; sub-project specifics go in the nested ones.

## Is this only for GitHub Copilot?

No — and this is the whole point of AGENTS.md existing as its own thing, separate from `copilot-instructions.md`. It's an open, vendor-neutral standard, read natively by a genuinely long list of tools: OpenAI Codex, Cursor, GitHub Copilot, Windsurf, Aider, Cline, Continue, Goose, Zed, and others — no per-tool setup, no configuration, the file just gets picked up because everyone agreed on the same filename and location.

One important exception, and it's easy to assume otherwise: **Claude Code does not read AGENTS.md natively.** It uses its own file, `CLAUDE.md`, and as of the most recent Claude Code release at the time of writing, Anthropic hasn't added native AGENTS.md support. There's a long-standing GitHub issue with thousands of upvotes asking for it, with no committed timeline.

The workaround, documented by Anthropic themselves, is either of:

```bash
# Option 1: symlink, Claude Code reads AGENTS.md through CLAUDE.md
ln -s AGENTS.md CLAUDE.md
```

```markdown
# Option 2: import syntax inside CLAUDE.md
@AGENTS.md
```

Either way, you maintain one canonical file and Claude Code effectively reads the same rules through the redirect. This is a fast-moving area — check current docs before committing to either workaround, since native support could land at any point.

## So how much workload does this actually save?

There's no controlled study behind this, and anyone who states a workload-savings number with total confidence is guessing too, same as anyone else. What's more useful is where the savings actually show up:

- **Code review time drops the most.** When every session generates code against the same architecture, reviewers stop spending attention on "why is this different from everywhere else" and start reviewing actual logic. That category of comment — the architectural-mismatch kind — is usually the first thing to shrink noticeably.

- **Rework drops next.** Fewer features get built against the wrong pattern in the first place, so fewer need partial rebuilding later. Harder to quantify, because it depends entirely on how much drift already existed before the fix — a project six months into inconsistency has more to unwind than one that catches it early.

- **Ramp-up time drops, but takes longer to show up.** Whether it's a new hire or just you returning to an old side project after a break, reading one file instead of reverse-engineering several competing patterns gets you productive faster. Real effect, slow to measure, since there's no clean baseline to compare against.

For an honest range instead of a fake precise number: **20–40% less time lost to inconsistency-driven rework and review friction** is a reasonable estimate — lower end for smaller projects that catch this early, higher end for larger ones that let drift run for months. Treat it as an estimate from pattern-watching, not a citable benchmark.

## Key takeaways

- This isn't a framework problem or a team-size problem — it happens any time an AI agent generates code without shared context, solo or at enterprise scale
- Solo, the drift shows up as inconsistency with your own earlier decisions; on a team, as competing "correct" implementations of the same thing
- AGENTS.md fixes it by giving every session the same architectural context before it generates anything
- It's genuinely open and tool-agnostic — read natively by Codex, Cursor, Copilot, Windsurf, Aider, and others — with one notable exception: Claude Code needs a symlink or import to pick up the same file
- It stops new drift; it doesn't retroactively fix code that's already inconsistent — budget separate time for that
- Workload savings are real but not precisely measurable — expect the biggest win in code review time, with rework and ramp-up improving more slowly and less visibly
