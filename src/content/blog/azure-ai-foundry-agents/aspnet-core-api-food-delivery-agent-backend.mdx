Picture the least glamorous moment in this whole series. Postman is open against the ASP.NET Core API of a food delivery app. There is a URL in the address bar with a few query parameters stuck on the end, a token in the headers tab, and a Send button. You click it, and JSON comes back: three dishes, spicy, none over RM20.

That is the system working. Everything the customer wanted was already in the database, and the answer took eleven milliseconds. The only problem is who did the work. **A person had to know that the parameter is called `maxPrice` and not `priceLimit`, that `spicy` takes a boolean, and that the whole thing hangs off `/api/catalog/dishes`.** Customers do not know any of that. They know how to type "something spicy under twenty ringgit".

Now put a Microsoft Foundry agent in front of that same URL. You describe the call once, in a schema, and hand it over. The customer types the sentence, the model picks `maxPrice=20` and `spicy=true`, your code sends exactly the request you just sent by hand, the same JSON comes back, and the agent turns it into a reply with the dish names in it.

Postman → URL → Foundry → response. The middle two are yours, and the URL is the one that has to exist first.

Which is where the reference project has a hole. [Part 2](../azure-ai-foundry-ai-agent-food-delivery-app) drew an architecture with an ASP.NET Core API sitting between the Flutter app and Foundry, and called it the trust boundary. Then I went looking for that API in the sample app and it does not exist — the app reads its menu directly from the client, so there is no server, and nothing for Foundry to call. This part builds it, and you can type along: a .NET Minimal API, a real SQL Server database, EF Core migrations, seed data, a Postman request that works, and then the agent on the end of it.

## What does the API actually need to expose?

Not everything. Work backwards from the nine tools the agent ends up with and you get a short list.

| Service method | Backs which tool | Returns |
| --- | --- | --- |
| `SearchDishesAsync` | `search_menu` | Dishes matching text, price ceiling, spice, diet |
| `SearchRestaurantsAsync` | `search_restaurant` | Restaurants matching text, cuisine, rating |
| `GetProfileAsync` | `get_user_profile` | Name, default address, recent orders |
| `AddToCartAsync` | `add_to_cart` | Updated cart total |
| `PlaceOrderAsync` | `create_order` | Order ID and status |
| `GetOrderStatusAsync` | `track_delivery` | Status, stage, ETA |
| `GetMenuPerformanceAsync` | `get_menu_performance` | Per-item orders and revenue |
| `GetPendingOrdersAsync` | `get_pending_orders` | Orders awaiting confirmation |
| `GetRiderQueueAsync` | `get_rider_queue` | Assigned orders with distances |

Nine methods. Note what they are not: they are not CRUD over your tables. Each one answers a question a human asked, which is why they map cleanly onto tools.

The walkthrough below builds the catalogue slice completely, from empty folder to Foundry reply, because once one vertical slice works the other eight are the same moves.

## Why SQL Server for an agent backend?

Look at what the agent gets asked. Spicy dishes under RM20. Orders still awaiting confirmation. Revenue per menu item this week. Those are filtered, sorted and aggregated queries over structured rows, which is the shape relational databases were built for. One `WHERE` clause per question, an index behind it, and a response in single-digit milliseconds.

It is also the store you can stand up in one command on any machine, which matters when the point is to follow along.

## What you need before the first command

- .NET 10 SDK, or any recent LTS. `dotnet --version` should print something.
- SQL Server. Windows developers already have LocalDB with Visual Studio; on macOS or Linux, Docker.
- A way to look at tables: SQL Server Management Studio, Azure Data Studio, or the VS Code mssql extension.
- Postman, or curl and `jq` if you prefer the terminal.
- For the last step only, a Microsoft Foundry project with a model deployed.

## Step 3 — Model the domain in C#

Two entities carry the catalogue. Only the fields the API actually uses:

```csharp
public class Restaurant
{
    public string Id { get; set; } = default!;
    public string Name { get; set; } = default!;
    public string Cuisine { get; set; } = default!;
    public double Rating { get; set; }
    public bool IsOpen { get; set; }
    public List<Dish> Dishes { get; set; } = [];
}

public class Dish
{
    public string Id { get; set; } = default!;
    public string RestaurantId { get; set; } = default!;
    public Restaurant Restaurant { get; set; } = default!;

    public string Name { get; set; } = default!;
    public string Description { get; set; } = "";
    public string? ImageUrl { get; set; }
    public decimal PriceMyr { get; set; }
    public decimal? DiscountPriceMyr { get; set; }

    public bool IsVegetarian { get; set; }
    public bool IsSpicy { get; set; }
    public int SpiceLevel { get; set; }
    public int PrepMinutes { get; set; }
    public bool IsPopular { get; set; }
    public bool IsAvailable { get; set; } = true;

    // Written by SQL Server, not by C# — see the next step.
    public decimal EffectivePrice { get; private set; }

    [NotMapped]
    public string RestaurantName => Restaurant?.Name ?? "";
}

public enum OrderStatus
{
    Placed, Confirmed, Preparing, ReadyForPickup, OutForDelivery, Delivered, Cancelled
}
```

`EffectivePrice` deserves the odd setter. In the Flutter app it is a getter on `FoodItem`: the discount price when there is one, otherwise the list price. The single worst bug in the first version of this system was the API filtering on `PriceMyr` while the app displayed the discounted value, so the agent quoted RM18.50 for a dish that cost RM14.90 at checkout. Nobody noticed for a week because both numbers looked plausible.

A computed C# property would not have fixed it either, because EF Core cannot translate one into SQL. Filter on it and you get a runtime exception, or worse, the whole table pulled into memory first. So the rule becomes: one definition, stored in the database, used by every query.

## Step 4 — The DbContext

```bash
dotnet add package Microsoft.EntityFrameworkCore.SqlServer
dotnet add package Microsoft.EntityFrameworkCore.Design
dotnet tool install --global dotnet-ef
```

```csharp
public class EatsDbContext(DbContextOptions<EatsDbContext> options) : DbContext(options)
{
    public DbSet<Restaurant> Restaurants => Set<Restaurant>();
    public DbSet<Dish> Dishes => Set<Dish>();

    protected override void OnModelCreating(ModelBuilder b)
    {
        b.Entity<Restaurant>(e =>
        {
            e.Property(r => r.Id).HasMaxLength(40);
            e.Property(r => r.Name).HasMaxLength(120).IsRequired();
            e.Property(r => r.Cuisine).HasMaxLength(60);
        });

        b.Entity<Dish>(e =>
        {
            e.Property(d => d.Id).HasMaxLength(40);
            e.Property(d => d.Name).HasMaxLength(120).IsRequired();
            e.Property(d => d.Description).HasMaxLength(600);

            // Money is decimal(10,2). Leave it to convention and you get
            // decimal(18,2) at best, a silent rounding bug at worst.
            e.Property(d => d.PriceMyr).HasPrecision(10, 2);
            e.Property(d => d.DiscountPriceMyr).HasPrecision(10, 2);

            // One definition of price, enforced by the database.
            e.Property(d => d.EffectivePrice)
             .HasPrecision(10, 2)
             .HasComputedColumnSql(
                 "CASE WHEN [DiscountPriceMyr] IS NOT NULL AND [DiscountPriceMyr] < [PriceMyr] " +
                 "THEN [DiscountPriceMyr] ELSE [PriceMyr] END", stored: true);

            // The agent's most common query, in index form.
            e.HasIndex(d => new { d.IsAvailable, d.IsSpicy, d.EffectivePrice });

            e.HasOne(d => d.Restaurant)
             .WithMany(r => r.Dishes)
             .HasForeignKey(d => d.RestaurantId)
             .OnDelete(DeleteBehavior.Cascade);
        });
    }
}
```

A stored computed column is indexable, which is the whole reason for `stored: true`. The index on those three columns is not premature: "available, spicy, under twenty ringgit" is the single query this system runs most.

## Step 7 — Seed the menu

Empty tables make every later step ambiguous. Seed the same dishes the Flutter app ships with, so the numbers in your API match the numbers on the phone screen.

```csharp
public static class EatsSeeder
{
    public static async Task SeedAsync(EatsDbContext db, CancellationToken ct = default)
    {
        if (await db.Restaurants.AnyAsync(ct)) return;

        var nasi = new Restaurant
        {
            Id = "r-nasi-lemak-house", Name = "Nasi Lemak House",
            Cuisine = "Malaysian", Rating = 4.6, IsOpen = true
        };

        db.Restaurants.Add(nasi);
        db.Dishes.AddRange(
            new Dish
            {
                Id = "d-spicy-chicken-rice", RestaurantId = nasi.Id,
                Name = "Spicy Chicken Rice",
                Description = "Steamed rice, sambal chicken, cucumber",
                PriceMyr = 14.00m, DiscountPriceMyr = 12.00m,
                IsSpicy = true, SpiceLevel = 1, PrepMinutes = 15, IsPopular = true
            },
            new Dish
            {
                Id = "d-sambal-prawn-rice", RestaurantId = nasi.Id,
                Name = "Sambal Prawn Fried Rice",
                Description = "Wok-fried rice with prawns and sambal",
                PriceMyr = 16.90m, IsSpicy = true, SpiceLevel = 2, PrepMinutes = 18
            });
        // The rest of the menu follows the same shape. Copy the items out of

    }

```

## Step 8 — The service layer

This is what the endpoint calls, and later what the agent's tool handler calls. Same method, two callers.

```csharp
public interface ICatalogService
{
    Task<IReadOnlyList<Dish>> SearchDishesAsync(
        string query,
        decimal? maxPriceMyr = null,
        bool spicy = false,
        bool vegetarian = false,
        int take = 8,
        CancellationToken ct = default);

    Task<IReadOnlyList<Restaurant>> SearchRestaurantsAsync(
        string query, string? cuisine = null, double? minRating = null,
        bool openNow = false, int take = 8, CancellationToken ct = default);
}
```

The implementation, deliberately boring:

```csharp
public sealed class CatalogService(EatsDbContext db) : ICatalogService
{
    public async Task<IReadOnlyList<Dish>> SearchDishesAsync(
        string query, decimal? maxPriceMyr, bool spicy, bool vegetarian,
        int take, CancellationToken ct)
    {
        var q = db.Dishes
            .AsNoTracking()
            .Include(d => d.Restaurant)
            .Where(d => d.IsAvailable);

        if (spicy) q = q.Where(d => d.IsSpicy);
        if (vegetarian) q = q.Where(d => d.IsVegetarian);
        if (maxPriceMyr is { } cap) q = q.Where(d => d.EffectivePrice <= cap);

        if (!string.IsNullOrWhiteSpace(query))
        {
            var like = $"%{query.Trim()}%";
            q = q.Where(d => EF.Functions.Like(d.Name, like)
                          || EF.Functions.Like(d.Description, like));
        }

        return await q
            .OrderByDescending(d => d.IsPopular)
            .ThenBy(d => d.EffectivePrice)
            .Take(Math.Clamp(take, 1, 20))
            .ToListAsync(ct);
    }
}
```

This is the method that finally answers "spicy food under RM20", the question that started the series in [Part 2](../azure-ai-foundry-ai-agent-food-delivery-app). No model involved yet. The intelligence needed was a `WHERE` clause the app never had.

Which is the point worth pausing on: **the agent is not what makes this possible, it is what makes it reachable from a sentence.** If you cannot write the service method, an agent will not rescue you.

Two SQL Server details hide in there. `Like` on a default collation is case-insensitive, so "SAMBAL" and "sambal" both match without any `ToLower()` — convenient, and a trap if you ever move the data somewhere case-sensitive. And `Math.Clamp` on `take` puts a ceiling on the row count before a model, or a curious user, asks for ten thousand.

## Step 9 — Two DTO shapes from one call

The app wants a full object to render a card. The model wants six fields it can read cheaply.

```csharp
// For the mobile app: everything the dish card renders.
public sealed record DishResponse(
    string Id, string Name, string RestaurantName, string Description,
    decimal Price, decimal? WasPrice, int SpiceLevel, bool IsVegetarian,
    int PrepMinutes, string? ImageUrl);

// For the agent: only what an answer needs.
public sealed record DishSummary(
    string Id, string Name, string RestaurantName,
    decimal Price, int SpiceLevel, int PrepMinutes);

public static class DishMapping
{
    public static DishResponse ToResponse(this Dish d) =>
        new(d.Id, d.Name, d.RestaurantName, d.Description,
            d.EffectivePrice,
            d.DiscountPriceMyr is not null ? d.PriceMyr : null,
            d.SpiceLevel, d.IsVegetarian, d.PrepMinutes, d.ImageUrl);

    public static DishSummary ToSummary(this Dish d) =>
        new(d.Id, d.Name, d.RestaurantName, d.EffectivePrice, d.SpiceLevel, d.PrepMinutes);
}
```

Two projections over one service call. I measured this later against real traffic: returning `DishResponse` to the model instead of `DishSummary` roughly doubled the cost of the most common turn and improved no answer.

## Step 10 — The endpoints and Program.cs

```csharp
public static class CatalogEndpoints
{
    public static void MapCatalog(this IEndpointRouteBuilder app)
    {
        var group = app.MapGroup("/api/catalog").RequireAuthorization();

        group.MapGet("/dishes", async (
            string? q, decimal? maxPrice, bool? spicy, bool? vegetarian,
            ICatalogService catalog, CancellationToken ct) =>
        {
            var dishes = await catalog.SearchDishesAsync(
                q ?? string.Empty, maxPrice, spicy ?? false, vegetarian ?? false, take: 20, ct);

            return Results.Ok(dishes.Select(d => d.ToResponse()));
        });
    }
}
```

## Step 12 — One test per service method

```csharp
[Fact]
public async Task Spicy_under_20_excludes_mild_and_expensive_dishes()
{
    await using var db = TestDb.Create();       // migrates + seeds a scratch database
    var service = new CatalogService(db);

    var results = await service.SearchDishesAsync("", maxPriceMyr: 20m, spicy: true);

    Assert.NotEmpty(results);
    Assert.All(results, d => Assert.True(d.IsSpicy));
    Assert.All(results, d => Assert.True(d.EffectivePrice <= 20m));

```

`TestDb.Create()` points at the same SQL Server with a throwaway database name, migrates it and seeds it. ## Step 13 — Hand the URL to Microsoft Foundry

Now the part the Postman request was rehearsing. The agent needs the same three facts you had in your head while filling in that form: where the call goes, what the parameters are called, and when it is worth making. You give it those as a **function tool** — a name, a description, and a JSON schema.

Add the Foundry packages:

```bash
dotnet add package Azure.AI.Projects --version 2.0.1
dotnet add package Azure.AI.Projects.Agents --version 2.0.0
dotnet add package Azure.Identity
```

Pin the versions. The 1.x line targets the older API and will not compile against any of this.

The tool definition is the Postman form, written down:

| What you did in Postman | What the tool definition says |
| --- | --- |
| Knew the route was `/api/catalog/dishes` | The handler, in your code |
| Typed `maxPrice=20` | `maxPriceMyr`, a number |
| Ticked `spicy=true` | `spicy`, a boolean |
| Decided this URL answered the question | The tool `description` |

```csharp
public static readonly FunctionTool SearchMenu = ResponseTool.CreateFunctionTool(
    functionName: "search_menu",
    functionDescription:
        "Finds dishes across all restaurants. Use for any request about food, cuisine, " +
        "spice, dietary needs or a price ceiling in Malaysian Ringgit. " +
        "Do not use for questions about an existing order.",
    functionParameters: BinaryData.FromObjectAsJson(new
    {
        type = "object",
        properties = new
        {
            query = new { type = "string", description = "Free text, e.g. 'nasi lemak'" },
            maxPriceMyr = new { type = "number", description = "Price ceiling in RM" },
            spicy = new { type = "boolean" },
            vegetarian = new { type = "boolean" }
        },
        required = new[] { "query" },
        additionalProperties = false
    }),
    strictModeEnabled: true);
```

That `functionDescription` carries real weight. It is the only thing the model reads when deciding whether this call is relevant, and the sentence starting "Do not use for" is what stops the agent calling your menu search to answer "where is my delivery".

```csharp
    agentName: config["Foundry:AgentName"], options: new(definition));
```

When the model decides to call the tool, your application is the one that runs it. The handler is four lines, and every one of them you have already written and tested:

```csharp
private async Task<string> SearchMenuAsync(JsonElement args, CancellationToken ct)
{
    var dishes = await catalog.SearchDishesAsync(
        args.GetProperty("query").GetString() ?? "",
        args.TryGetProperty("maxPriceMyr", out var p) ? p.GetDecimal() : null,
        spicy: args.TryGetProperty("spicy", out var s) && s.GetBoolean(),
        vegetarian: args.TryGetProperty("vegetarian", out var v) && v.GetBoolean(),
        take: 8, ct);

    return JsonSerializer.Serialize(dishes.Select(d => d.ToSummary()));
}
```

<Callout type="warning" title="The portal cannot define function tools">
You can run an agent that has function tools in the Foundry portal, but you cannot add, remove or update function definitions there, and the playground will not execute them because no application is listening on the other end. The definition above belongs in code, which also puts your production instructions under version control.
</Callout>

Ask it "something spicy under twenty ringgit" and the round trip reads like this:

```text
customer  →  "anything spicy under twenty ringgit?"
model     →  search_menu { "query": "", "maxPriceMyr": 20, "spicy": true }
your code →  CatalogService.SearchDishesAsync(...)  →  SQL Server
your code →  [{"name":"Spicy Chicken Rice","price":12.00,"spiceLevel":1}, …]
agent     →  "Three spicy options under RM20. Spicy Chicken Rice is RM12
              and ready in 15 minutes…"
```

Line three is the request you sent in Postman. Line four is the response you read there, minus the fields a model does not need. Nothing new happened in the data layer at all — the agent only supplied the parameters and the sentence at each end.

## Key takeaways

- The URL comes first. A Foundry agent is a caller, and it can only be as good as the endpoint it calls.
- Test the exact call in Postman before a model sees it, so a wrong answer later has one fewer suspect.
- Work backwards from the tools you want. Nine question-shaped service methods beat a generic CRUD API.
- Store price logic as a computed column so C#, SQL and the mobile app can never disagree about what a dish costs.
- Project two DTO shapes from one service call: full for the app, trimmed for the model.
- A function tool is your Postman form written as a schema, and its `description` is what decides whether the model calls it at all.
