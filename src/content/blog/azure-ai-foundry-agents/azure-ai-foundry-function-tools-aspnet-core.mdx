Everything here runs in ASP.NET Core, because that is where the tool code has to live: your API already knows how to authenticate a caller, validate a request and write a log line, and a tool that skips all three is a liability. The agent calls your API. Your API does not become the agent.

## Which tools should the agent get?

I gave the first version too many tools, watched it pick the wrong one repeatedly, and cut back. This is the set that survived, split by the role allowed to call it.

| Tool | Role | Input | Returns |
| --- | --- | --- | --- |
| `search_menu` | Customer | `query`, `maxPriceMyr`, `spicy`, `vegetarian` | Up to 8 dishes: name, restaurant, price, spice level |
| `search_restaurant` | Customer | `query`, `cuisine`, `openNow`, `minRating` | Up to 8 restaurants with rating and delivery fee |
| `get_user_profile` | Customer | none | Name, default address, last 3 orders |
| `add_to_cart` | Customer | `foodItemId`, `quantity` | Updated cart total |
| `create_order` | Customer | `paymentMethod`, `addressId` | Order ID and status |
| `track_delivery` | Customer | `orderId` (optional) | Status, stage, rider ETA |
| `get_menu_performance` | Partner | `days` (1-30) | Per-item orders, revenue, trend |
| `get_pending_orders` | Partner | none | Orders awaiting confirmation, oldest first |
| `get_rider_queue` | Rider | none | Assigned orders with pickup and drop distances |

Three rules produced that table, and I would carry all three to any other agent.

**No tool takes an identity parameter.** Not `userId`, not `restaurantId`, not `riderId`. If the model cannot pass it, the model cannot get it wrong, and no amount of clever prompting by a hostile user can make it get it wrong either. This is important enough that [Part 6 is mostly about it](../azure-ai-foundry-agent-security-jwt-roles).

**Read tools are generous, write tools are narrow.** `search_menu` can be called freely. `create_order` runs only after the customer has confirmed in the UI.

**Tool output is trimmed to what the answer needs.** `search_menu` returns eight dishes with six fields each, not the full `FoodItem` with allergens, ingredients and image URLs. Every extra field is tokens on every call, and one more thing the model can misquote.

## How do you declare a function tool in C#?

A function tool is a name, a description the model reads, and a JSON Schema for the arguments.

```csharp
public static class EatsTools
{
    public static readonly FunctionTool SearchMenu = ResponseTool.CreateFunctionTool(
        functionName: "search_menu",
        functionDescription:
            "Finds dishes across all restaurants. Use for any request about food, " +
            "cuisine, spice, dietary needs or a price ceiling in Malaysian Ringgit. " +
            "Do not use for questions about an existing order.",
        functionParameters: BinaryData.FromObjectAsJson(new
        {
            type = "object",
            properties = new
            {
                query = new { type = "string", description = "Free text, e.g. 'nasi lemak'" },
                maxPriceMyr = new { type = "number", description = "Price ceiling in RM" },
                spicy = new { type = "boolean" },
                vegetarian = new { type = "boolean" }
            },
            required = new[] { "query" },
            additionalProperties = false
        }),
        strictModeEnabled: true);
}
```

Register them on the agent definition from [Part 4](../azure-ai-foundry-project-setup-first-agent):

```csharp
var definition = new DeclarativeAgentDefinition(model: config["Foundry:ModelDeployment"])
{
    Instructions = await File.ReadAllTextAsync("Agents/Instructions/eats-assistant.md"),
    Tools =
    {
        EatsTools.SearchMenu, EatsTools.SearchRestaurant, EatsTools.GetUserProfile,
        EatsTools.AddToCart, EatsTools.CreateOrder, EatsTools.TrackDelivery,
        EatsTools.GetMenuPerformance, EatsTools.GetPendingOrders, EatsTools.GetRiderQueue
    }
};
```

Two mistakes I made on the first attempt are worth stealing.

The description originally read "Searches the menu", which told the model nothing about when *not* to use it, so it cheerfully called `search_menu` for "where is my delivery". The sentence beginning "Do not use for" cut that failure to near zero. Write descriptions as routing rules, because that is what they are.

I also left `strictModeEnabled` off, which meant the model occasionally sent `maxPriceMyr` as the string `"20"` instead of the number `20`. Turning strict mode on made schema conformance the service's problem instead of mine.


`AIProjectClient` is thread-safe and expensive to build, so it is a singleton. The executor is scoped because it resolves per-request services, including the caller's identity.

## The run loop

This is the heart of the integration. It sends the user's message, handles any function calls, and loops until the model produces text.

```csharp
public sealed class AgentConversationService(
    AIProjectClient projectClient,
    IToolExecutor executor,
    IConfiguration cfg,
    ILogger<AgentConversationService> logger)
{
    private const int MaxToolRounds = 5;

    public async Task<AgentReply> AskAsync(
        string userMessage, string? conversationId, CallerContext caller, CancellationToken ct)
    {
        var responses = projectClient.ProjectOpenAIClient
            .GetProjectResponsesClientForAgent(cfg["Foundry:AgentName"]);

        var inputItems = new List<ResponseItem> { ResponseItem.CreateUserMessageItem(userMessage) };
        string? previousResponseId = conversationId;
        ResponseResult response;
        var rounds = 0;

        do
        {
            response = await responses.CreateResponseAsync(
                previousResponseId: previousResponseId,
                inputItems: inputItems,
                cancellationToken: ct);

            previousResponseId = response.Id;
            inputItems.Clear();
            var calledSomething = false;

            foreach (ResponseItem item in response.OutputItems)
            {
                inputItems.Add(item);

                if (item is FunctionCallResponseItem call)
                {
                    logger.LogInformation(
                        "Agent tool {Tool} for {Role} user {UserId}",
                        call.FunctionName, caller.Role, caller.UserId);

                    // Identity is supplied here, never by the model.
                    string output = await executor.ExecuteAsync(
                        call.FunctionName, call.FunctionArguments, caller, ct);

                    inputItems.Add(ResponseItem.CreateFunctionCallOutputItem(call.CallId, output));
                    calledSomething = true;
                }
            }

            if (!calledSomething) break;
        }
        while (++rounds < MaxToolRounds);

        return new AgentReply(response.GetOutputText(), response.Id);
    }
}
```

Three details in there are load-bearing.

`MaxToolRounds` is not decoration. In the first week in staging, a badly worded tool description sent the model into a loop calling `search_restaurant` with slightly different arguments seven times for one question. Each round is a paid model call. Cap it, log when you hit the cap, and treat hitting the cap as a bug in a tool description rather than a bug in the model.

A single response can contain several `function_call` items at once, so the loop handles all of them in one round before replying. Serialising them into separate rounds would work and would cost more.

<Callout type="warning" title="Runs expire after ten minutes">
Foundry expires a run ten minutes after creation, so tool outputs must be submitted inside that window. A tool that blocks on a slow downstream call can lose the whole turn. Anything slow should return a status immediately and be polled separately.
</Callout>

## The executor

The executor maps a tool name to a method, and it is where the checks live.

```csharp
public async Task<string> ExecuteAsync(
    string toolName, BinaryData arguments, CallerContext caller, CancellationToken ct)
{
    if (!ToolCatalog.IsAllowedFor(toolName, caller.Role))
    {
        logger.LogWarning("Blocked {Tool} for role {Role}", toolName, caller.Role);
        return """{"error":"not_permitted","message":"This action is not available to you."}""";
    }

    try
    {
        using var json = JsonDocument.Parse(arguments);

        return toolName switch
        {
            "search_menu"        => await SearchMenuAsync(json.RootElement, ct),
            "get_user_profile"   => await GetProfileAsync(caller.UserId, ct),
            "add_to_cart"        => await AddToCartAsync(json.RootElement, caller.UserId, ct),
            "track_delivery"     => await TrackAsync(json.RootElement, caller.UserId, ct),
            "get_pending_orders" => await PendingAsync(caller.RestaurantId!, ct),
            "get_rider_queue"    => await RiderQueueAsync(caller.UserId, ct),
            _ => """{"error":"unknown_tool"}"""
        };
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "Tool {Tool} failed", toolName);
        return """{"error":"tool_failed","message":"That lookup failed. Please try again."}""";
    }
}
```

Read that `switch` carefully. Every identity value comes from `caller`, built from the validated token. Nothing that decides *whose* data this is came out of `json.RootElement`. The model picks the verb; the server picks the noun.

The catch block returns an error string instead of throwing. That was a deliberate change after an early version where a null reference in one tool killed the run and the customer got a spinner that never resolved. Handing the model a structured error lets it say "I could not check that order, please try again" and stay in the conversation.

## Validating what the model sent you

Each handler validates its own arguments, and it is ordinary defensive code:

```csharp
private async Task<string> SearchMenuAsync(JsonElement args, CancellationToken ct)
{
    var query = args.GetProperty("query").GetString() ?? string.Empty;
    if (query.Length > 120) query = query[..120];

    decimal? maxPrice = args.TryGetProperty("maxPriceMyr", out var p) && p.TryGetDecimal(out var d)
        ? Math.Clamp(d, 0m, 500m)
        : null;

    var dishes = await catalog.SearchDishesAsync(query, maxPrice,
        spicy: args.TryGetProperty("spicy", out var s) && s.GetBoolean(),
        vegetarian: args.TryGetProperty("vegetarian", out var v) && v.GetBoolean(),
        take: 8, ct);

    // Only what the answer needs. Six fields, not twenty.
    return JsonSerializer.Serialize(dishes.Select(x => new
    {
        x.Id, x.Name, x.RestaurantName, Price = x.EffectivePrice, x.SpiceLevel, x.PrepMinutes
    }));
}
```

`Math.Clamp` on a number the model produced from user text is not paranoia. It is the same reason you clamp a page size on a public endpoint: the value travelled through something you do not control before it reached you.

Notice also what `SearchDishesAsync` is. It is not a new query written for the agent, it is the same catalogue call the app's own search screen uses. Tools that wrap existing endpoints inherit the authorization, validation and logging you already reviewed. Tools that reach past them into the database are a second data path with none of it, and it will be the one nobody remembers to audit.

## The endpoint

```csharp
[Authorize]
[HttpPost("/api/assistant/ask")]
public async Task<ActionResult<AgentReply>> Ask(
    [FromBody] AskRequest request, CancellationToken ct)
{
    if (request.Message.Length > 1000) return BadRequest("Message too long.");

    var caller = CallerContext.FromClaims(User);
    var reply = await agent.AskAsync(request.Message, request.ConversationId, caller, ct);
    return Ok(reply);
}
```

## Key takeaways

- Write tool descriptions as routing rules. A sentence saying when the tool does not apply is worth more than a paragraph about what it does.
- Turn on strict mode so schema conformance is the service's problem, not your parsing code's.
- Cap the tool rounds. An unbounded loop is a paid loop.
- Handle several function calls from one response in a single round.
- Catch exceptions in the executor and return a structured error string. A thrown exception kills the run.
- Clamp and truncate every argument the model sends. Those values started life as user text.
- Wrap existing business endpoints rather than writing fresh database queries for the agent.
