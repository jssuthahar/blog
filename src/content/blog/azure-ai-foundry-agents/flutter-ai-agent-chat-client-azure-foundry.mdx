## What has to be added to the app?

The app currently talks to a seeded demo backend or Firestore, selected by `AppConfig.backend`. It has no HTTP client for a custom API, so this is genuinely new code. It follows the repository's existing conventions rather than inventing new ones.

```yaml
dependencies:
  http: ^1.2.2   # the only addition
```

One package. If your app already has `dio`, use that instead; nothing here depends on the client.

## The domain contract

A contract in `lib/domain/repositories/assistant_repository.dart`, pure Dart, no Flutter import:

```dart
class AssistantReply {
  const AssistantReply({required this.text, required this.conversationId});

  final String text;
  final String conversationId;
}

abstract interface class AssistantRepository {
  Future<Result<AssistantReply>> ask(String message, {String? conversationId});
}
```

`Result<T>` is the app's existing sealed type, `Success` or `FailureResult`, chosen so failure handling is part of the signature and the presentation layer cannot forget an error path. The assistant gets no special treatment.

## The implementation

In `lib/data/repositories/assistant_repository_impl.dart`. `guard` is the app's existing helper that converts any thrown `AppException` into a `Failure`, so exception-to-failure mapping stays in exactly one place:

```dart
class AssistantRepositoryImpl implements AssistantRepository {
  AssistantRepositoryImpl({required http.Client client, required AuthTokenProvider tokens})
      : _client = client,
        _tokens = tokens;

  final http.Client _client;
  final AuthTokenProvider _tokens;

  @override
  Future<Result<AssistantReply>> ask(String message, {String? conversationId}) {
    return guard(() async {
      final String token = await _tokens.idToken();

      final http.Response response = await _client
          .post(
            Uri.parse('${AppConfig.instance.apiBaseUrl}/api/assistant/ask'),
            headers: <String, String>{
              'Authorization': 'Bearer $token',
              'Content-Type': 'application/json',
            },
            body: jsonEncode(<String, dynamic>{
              'message': message,
              'conversationId': conversationId,
            }),
          )
          .timeout(const Duration(seconds: 45));

      if (response.statusCode == 401) {
        throw AuthException('Your session expired. Please sign in again.');
      }
      if (response.statusCode != 200) {
        throw ServerException('Assistant unavailable (${response.statusCode})');
      }

      final Map<String, dynamic> json =
          jsonDecode(response.body) as Map<String, dynamic>;

      return AssistantReply(
        text: json['reply'] as String,
        conversationId: json['conversationId'] as String,
      );
    });
  }
}
```

That 45 second timeout is not generous, it is realistic. An agent turn with two tool calls routinely takes four to nine seconds, and the tail is much longer than a normal API call because a slow tool adds a full model round trip behind it. Set the timeout from measured latency, not from the three seconds you use elsewhere.

`apiBaseUrl` is a new field on `AppConfig`, which is already the app's single place for this kind of setting.

## The Cubit

The conversation ID is the only state that has to survive between turns. The transcript lives server-side in Foundry, so the client holds one string.

```dart
class AssistantCubit extends Cubit<AssistantState> {
  AssistantCubit(this._repository) : super(const AssistantState());

  final AssistantRepository _repository;
  String? _conversationId;

  Future<void> send(String message) async {
    emit(state.copyWith(
      messages: <ChatMessage>[...state.messages, ChatMessage.user(message)],
      status: AssistantStatus.thinking,
    ));

    final Result<AssistantReply> result =
        await _repository.ask(message, conversationId: _conversationId);

    result.fold(
      (Failure failure) => emit(state.copyWith(
        status: AssistantStatus.failure,
        errorMessage: failure.message,
      )),
      (AssistantReply reply) {
        _conversationId = reply.conversationId;
        emit(state.copyWith(
          messages: <ChatMessage>[...state.messages, ChatMessage.agent(reply.text)],
          status: AssistantStatus.idle,
        ));
      },
    );
  }

  void startNewConversation() {
    _conversationId = null;
    emit(const AssistantState());
  }
}
```

`startNewConversation` exists because conversations accumulate context and context costs tokens. A "new chat" affordance is a cost control disguised as a UI feature.

Register the repository in `lib/app/di/service_locator.dart` alongside the others and add the route in `lib/app/router/`. Blocs stay out of `get_it` in this project by convention, so the Cubit is created at the screen.

## Two UI decisions that mattered more than the code

### Name the step, do not spin

Five seconds of an undifferentiated spinner feels broken. Five seconds of "checking the menu" does not, and it is the same five seconds.

```dart
Widget _thinkingIndicator(AssistantState state) {
  return Row(
    children: <Widget>[
      const SizedBox(
        width: 14, height: 14,
        child: CircularProgressIndicator(strokeWidth: 2),
      ),
      const SizedBox(width: 10),
      Text(state.hint ?? 'Thinking…', style: Theme.of(context).textTheme.bodySmall),
    ],
  );
}
```

The server sets the hint from the tool it is about to run, returned on a streaming channel or simply inferred client-side from the message text. Even a rough guess beats a bare spinner.

### Confirm anything that writes

When the agent proposes an order, the app does not let the model place it. It renders the proposal as a card with a real button, and `create_order` runs from that button press.

```dart
if (message.proposal != null)
  OrderProposalCard(
    proposal: message.proposal!,
    onConfirm: () => context.read<CheckoutCubit>().placeOrder(message.proposal!),
  ),
```

The model asks, the human confirms, the API acts. This is not only a safety property; it is also the difference between an assistant people trust with money and one they use twice.

## Testing the Flutter side

No test here needs a model, a network call or an API key, because the agent is behind an interface. This is the same `bloc_test` and `mocktail` setup the rest of the app uses.

```dart
class _FakeAssistantRepository extends Mock implements AssistantRepository {}

blocTest<AssistantCubit, AssistantState>(
  'emits thinking then the agent reply, and keeps the conversation id',
  build: () {
    when(() => repository.ask(any(), conversationId: any(named: 'conversationId')))
        .thenAnswer((_) async => const Result<AssistantReply>.success(
              AssistantReply(text: 'Three spicy dishes…', conversationId: 'conv_1'),
            ));
    return AssistantCubit(repository);
  },
  act: (AssistantCubit cubit) => cubit.send('Find spicy food under RM20'),
  expect: () => <Matcher>[
    isA<AssistantState>().having((AssistantState s) => s.status, 'status', AssistantStatus.thinking),
    isA<AssistantState>()
        .having((AssistantState s) => s.status, 'status', AssistantStatus.idle)
        .having((AssistantState s) => s.messages.last.text, 'reply', contains('spicy')),
  ],
);

blocTest<AssistantCubit, AssistantState>(
  'surfaces a failure message instead of throwing',
  build: () {
    when(() => repository.ask(any(), conversationId: any(named: 'conversationId')))
        .thenAnswer((_) async => const Result<AssistantReply>.failure(
              ServerFailure('Assistant unavailable'),
            ));
    return AssistantCubit(repository);
  },
  act: (AssistantCubit cubit) => cubit.send('hello'),
  expect: () => <Matcher>[
    isA<AssistantState>().having((AssistantState s) => s.status, 'status', AssistantStatus.thinking),
    isA<AssistantState>().having((AssistantState s) => s.status, 'status', AssistantStatus.failure),
  ],
);
```

The second test is the one that matters on a phone. Networks fail, tokens expire, and Foundry has outages like everything else. The assistant screen shows an error with a link to normal search, and the ordering flow never depends on the agent being up. Degrade to the app you already have.

The whole path now works end to end, phone to API to agent and back. What it has not met yet is real traffic — tracing, token cost, and the failures that only appear at volume.

## Key takeaways

- Put the agent behind a repository interface. The widget tree should not know a model exists.
- Set the client timeout from measured agent latency. 45 seconds is realistic; 3 seconds is not.
- The client only needs the conversation ID. Turn history lives server-side.
- Offer a "new chat" action. Long conversations cost tokens on every turn.
- Name the step instead of showing a bare spinner. Same wait, different feeling.
- Render write actions as a proposal with a real button. The model asks, the human confirms.
- Test the Cubit against a fake repository, so no test needs a model or a key.
